# YAN-359 SSO JIT — Recommendations

## Executive Summary

Build one shared SSO admission path after protocol verification, backed by existing identity, user, workspace, bootstrap and session primitives. Current callbacks already extract stable OIDC/SAML keys, but `sessionClaims()` admits only linked owners and still falls back to owner for unlinked SSO while one active user exists; replace that fallback only on the enabled JIT path.

Target `master`, v1.1.0, behind `isMultiUserEnabled()` / `requireMultiUser()`. No backport, new dependency, production IdP call or application change in this research task. Parent owns synthesis and validation; findings below come from direct inspection, not other researchers' reports.

Sources: [YAN-359](https://linear.app/yandy-r/issue/YAN-359), main-checkout `docs/users/README.md`, `docs/users/spec.md`, `docs/users/adr/0003-identity-and-bootstrap.md`; worktree inspected at `dcae2aa3`.

## Implementation Recommendations

### Approach

- **Stable identity first:** require nonempty verified `issuer` and `subject`, find by `(provider, issuer, subject)`, then reuse `resolveSsoUser()` for explicit one-shot owner linking. Otherwise provision new user, never infer ownership or account linkage from email. Same subject under another issuer is another identity.
- **Admission before mutation:** validate policy and derive groups before owner linking, JIT creation or membership writes. Reject disallowed users without minting cookies or spending setup credentials. Reject disabled linked users before role synchronization; IdP claims must not reactivate them.
- **Default pending:** create user, personal workspace, personal owner membership and identity atomically. `createUserUnscoped()` already creates the first three, but returns from its own transaction before `linkIdentityUnscoped()` can run. Add a small synchronous transaction seam rather than wrapping asynchronous repo calls in `db.transaction()`; existing adapter transactions are synchronous. Unique-identity race must roll back loser’s whole JIT creation, then resolve winner deterministically.
- **One sync transaction:** derive desired instance role and shared-workspace memberships; preserve owner role and every `manual`/`invite` membership. Only mutate rows with `source='idp'`. Update login timestamps, bump `sv` when actual access changes, invalidate user caches, and mint fresh claims from committed state. Repeated unchanged login must not revoke sessions.
- **Pending UI without session:** reuse `/login?error=account_pending` and existing `loginErrors.js` message, with explicit waiting-for-approval presentation if product requires a dedicated page. Do not make pending JWTs valid to satisfy UI. Current `validateSessionToken()` and `passwordSessionClaims()` correctly reject pending users.
- **Policy settings:** prefer one bounded instance settings object (proposed `ssoJit`: `groupsClaim`, `allowedGroups`, `adminGroups`, `groupWorkspaceMap`, `defaultRole`) rather than a new settings system. Keep policy GET/PATCH hidden while switch off; reuse existing admin-only settings authorization and validation, or add one narrowly scoped endpoint with declarative route-policy entry. Full mapping editor belongs to YAN-373, not this issue.
- **Email linking:** defer general opt-in email merging. YAN-359 forbids implicit email merge; implementing another merge mode increases takeover surface without meeting additional acceptance criteria. Explicit owner bootstrap remains supported exactly as ADR-0003 specifies.

Use native `fetch` and `AbortSignal.timeout()` for UserInfo; installed `jose` and `@node-saml/node-saml` remain protocol verifiers. Dot-path claim lookup should traverse own properties only, accept string arrays or a documented scalar-string form, reject objects/non-string values, and never mutate claim objects. SAML attribute names may be URI strings containing periods: try exact configured attribute key before nested-path interpretation.

UserInfo fallback means **claim absent**, not empty array. If groups exist in id_token, do not merge additional UserInfo groups. Require UserInfo `sub` equal verified id_token `sub`; keep identity issuer/subject from id_token. Fetch only when switch on, claim missing and endpoint/access token available; transport failure must not silently erase memberships or demote accounts. Do not persist or log access token.

### Phasing and quick wins

Freeze policy shape and conflict rules first. Then protocol extraction and transactional DB work can proceed independently. Connect callbacks only after both exist; add policy API and pending presentation after core admission is proven. Existing `account_pending` message and callbacks’ audit calls reduce UI and observability work.

## Improvement Ideas

- **Defer to YAN-373:** group mapping editor, workspace picker, preview/dry-run UI and approval controls. This issue needs validated backend settings and understandable denial/pending states only.
- **Defer general email merge:** only add with explicit administrator consent, verified email, secure account-link proof and dedicated takeover tests.
- **Defer background group polling / SCIM:** login-time re-evaluation is binding scope. Document that upstream changes affect tokenhop at next login, not immediately.
- **Small operational improvement now:** audit role/membership deltas and denied policy outcomes using stable codes, without emails, claim dumps, tokens or setup credentials. Reuse audit pipeline; no new telemetry subsystem.
- **Defer multi-IdP management / provenance schema expansion:** current configuration chooses SSO mode and identity table already distinguishes issuers. Add provider-specific membership provenance only when multiple configured IdPs require independent synchronization.

Integration challenges: existing `tests/unit/oidc-callback.test.js` mocks `sessionClaims()` and therefore proves verification wiring, not real admission. Existing bootstrap test "first SSO login is NOT owner" checks identity linking, while session-level fallback still differs; assertions need end-to-end admission coverage. Approval APIs/editor are not present beyond user password endpoint; do not expand YAN-359 into YAN-360/373.

Security boundary: claim readers consume only verified payloads/profiles. Public login responses contain fixed codes; server logs and audit omit claim dumps, token material, assertion XML and setup-token values. Owner link proof must remain single use under concurrent callbacks.

## Key Decisions Needed

- Role authority after approval: avoid resetting every manually approved `user` to `pending` just because default remains pending. Define which roles IdP owns and how admin-group removal demotes manual admins.
- Conflict resolution when multiple groups map one workspace: deterministic rank (proposed `manager > member > viewer`; omit mapped `owner` unless explicitly required), with manual/invite row unchanged. Policy must be documented and tested.
- Last-manager removal: reject invalid sync with actionable recovery rather than silently retaining revoked access. Decide whether save-time restrictions suffice and how operator repairs stale existing maps.
- Owner and allow-list: recommended all SSO admissions honor configured allow-list, including owner. Preserve password/host recovery; do not introduce undocumented owner bypass.
- Settings API shape and pending presentation: one bounded object, existing administrator settings path if practical; no unnecessary dedicated pending cookie/session/API.

## Open Questions

- Does Linear checklist require optional general admin email-linking configuration now, or only enforce safety if added later? Recommended defer; no implicit merge permitted either way.
- How should group-source absence with no UserInfo endpoint behave under configured mapping? Recommended fail closed when authorization needs missing data; distinguish confirmed empty groups from unavailable groups to avoid accidental destructive sync.
- How should SAML transient NameID be handled: explicit rejection or documented persistent-identifier precondition? Verified NameID must not be substituted with email.
- Should invalid workspace references block whole login or only mapping writes? Recommended atomic failure and visible operator remediation; never partial grant/sync.
- Blocker completion/merge ancestry not audited here. Parent must verify YAN-349/604/356/357 Done and merged into current `origin/master`; inspected code already contains their relevant helper paths.
