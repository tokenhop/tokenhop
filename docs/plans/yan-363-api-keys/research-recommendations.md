# YAN-363 API keys — Recommendations Research

## Executive Summary

Hashing `apiKeys.key` breaks more than authentication: model probes, MITM startup/restart, CLI installation flows, Codex cleanup, usage joins, and DB import/export all consume recoverable keys. Land schema/auth changes only with bounded compatibility changes or explicit switch-on refusal at these edges; never substitute display prefixes or constant fallback keys for credentials.

Research verified against worktree `users/yan-363-api-keys`, HEAD `bf80e10a`. Source: GH #231 fetched with `gh issue view 231 --repo tokenhop/tokenhop --json title,body`; main-checkout ignored `docs/users/spec.md`, handbook §5, ADR-0005. Issue body conflicts with approved ADR: use HMAC/HKDF and dedicated MITM internal credential, not plain SHA-256 or a recoverable service-key reference. Resolve remaining ownership conflicts before implementation.

## Implementation Recommendations

### Approach and technology choices

- Use Node crypto and existing DB/migration, principal, capability, and test machinery. No new dependency, generic credential vault, or auth framework.
- Preserve switch-off behavior on installations never migrated. `src/lib/users/featureSwitch.js` is sole switch reader. Do not replace existing `/api/keys` routes with unconditional `requireMultiUser()` 404s: legacy routes must remain usable.
- Keep credential material at ingress/creation and explicit client configuration boundaries. Pass key identity/scopes downstream, not presented bearer tokens. Distinguish gateway client keys from upstream `credentials.apiKey`; globally renaming or stripping every `apiKey` would break provider calls.
- Make persistence mode explicit after migration. An irreversible dropped `key` column cannot support legacy queries merely because switch later becomes off. Require approved behavior for on-to-off transition; do not claim lossless rollback. ADR-0009 specifies backup restore for downgrade after irreversible migrations.
- Reuse shared extraction (`src/lib/auth/clientApiKey.js`) and existing principal integration. Avoid confusing auth resolver with unrelated `resolveApiKey` already exported by `src/lib/cliToolConfigs/shared.js`.

### Logging boundary

`open-sse/utils/requestLogger.js:99-144` already masks credential headers, case-insensitively, including `x-goog-api-key`. `src/lib/db/repos/requestDetailsRepo.js:93-103,147` removes sensitive headers before persistence. Reuse existing redaction rather than duplicate it. Header redaction is not proof that raw-key usage fields, preset values, request URL query parameters, or config-text responses are safe. `clientApiKey.js` accepts URL `key`; exercise that transport explicitly with logging enabled. Inspect stored values and captured outputs, not only property names.

### Phasing and quick wins

1. Freeze migration/response contracts; inventory exact secret consumers and establish failing sentinel tests before irreversible migration.
2. Add hash/master-key lifecycle and migration with backup, stable IDs, legacy validation and default-workspace assignment. Preserve unmigrated off-mode SQL/response semantics.
3. Connect resolver/principal, scope/expiry/lifecycle enforcement, and ID-only usage handoff across all handler paths. Resolve usage ownership with YAN-370 before claiming full no-raw-key guarantee.
4. Repair bounded consumers: MITM/probes, CLI display/setup, safe responses, export/import compatibility. Full CLI-tools tenancy and export redesign remain assigned follow-ups.
5. Run feature gate both ways and restore rehearsal; inspect production build and published CLI source coverage separately.

## Improvement Ideas

Only in-scope improvements: common metadata projection for key responses; shared gateway identity extraction; reuse existing typed-key-in-memory setup path; one parameterized credential-transport/handler matrix. Defer budgets, key rotation commands, new vault storage, provider-sharing policy and new UI frameworks to owning issues.

## Task Breakdown Preview

- Contract/test fixtures — medium: switch transitions, scope matrix, sentinel scanner, migration fixture.
- Crypto/persistence — high: shared master-key loader, hashKid, guarded reshape/backup, legacy importer compatibility.
- Auth/lifecycle — high: all ingress paths, owner/service principal mapping, scopes, cache invalidation.
- Existing usage boundary — medium/high: ID propagation, all response modes, legacy joins and metadata cleanup; coordinate YAN-370.
- Integration repairs — medium/high: MITM credential lifecycle, probes, CLI/browser recovery removal, config readback and import/export guard.
- Verification — high: both switch states, targeted matrix, lint/test/build/brand checks, backup restore. Estimates indicate relative complexity, not committed duration.

## Key Decisions Needed

1. Confirm ADR-0005 supersedes older issue bullets: HMAC/HKDF, `th_` format, internal MITM credential. Issue says plain SHA-256/service-key setting; approved design says otherwise.
2. Decide minimum YAN-370/374/375 overlap needed for “no raw key except creation.” Leaving existing secret sinks operational does not satisfy that acceptance condition.
3. Define post-enable switch-off behavior. Original raw display cannot be recovered after hashing; restore is not equivalent to ordinary feature-toggle reversal.
4. Specify internal MITM principal, gateway validation, hash replacement on cold boot, and whether configured remote router is supported. Current route accepts `mitmRouterBaseUrl`; local-only assumptions need enforcement, not inference.
5. Specify hashKid retention before any master-key rotation. ADR requires old derived keys remain loadable; new rotation commands remain deferred.
