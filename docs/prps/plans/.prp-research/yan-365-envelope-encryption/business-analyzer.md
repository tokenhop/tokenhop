## User Stories

| ID   | As a                                                       | I want                                                                                           | So that                                                | Decision / claim |
| ---- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------ | ---------------- |
| US1  | instance owner enabling multi-user                         | existing credentials encrypted once, after a verified backup                                     | a stolen DB, backup or export leaks no tokens          | D7, D10 / C1, C3 |
| US2  | instance owner                                             | CLI and admin-API KEK rotation                                                                   | I can recover from exposure of the root key            | D8, D9 / C5      |
| US3  | gateway client using an existing `th_` or legacy `sk-` key | my key to keep authenticating after a KEK rotation and restart                                   | rotation causes no client outage                       | D6 / C5          |
| US4  | instance owner                                             | per-workspace DEK rotation, where rotating Default re-encrypts the SSO and MITM secrets          | one workspace's exposure is contained                  | D5, D8 / C6      |
| US5  | workspace member                                           | my credentials bound to my workspace, row and field                                              | nobody can swap or reuse my ciphertext                 | D1 / C2          |
| US6  | owner who disables the switch after activation             | encryption to stay in force                                                                      | turning the switch off never downgrades security       | D4 / C10         |
| US7  | single-user operator who never enabled multi-user          | an upgrade that changes nothing                                                                  | I don't take on a key-backup duty unexpectedly         | D4 / C10         |
| US8  | owner deleting a workspace                                 | its DEK destroyed and the cache evicted, with an honest statement of what this cannot reach      | live data is shredded and my expectations are accurate | D5, D7 / C7      |
| US9  | owner restoring a backup                                   | a wrong or missing KEK rejected before any wipe, and a same-KEK restore that recovers everything | I never destroy live data with an unreadable restore   | D3, D8 / C4, C9  |
| US10 | owner with a stored MITM sudo password                     | the legacy value re-keyed exactly once, with activation aborting if it can't be decrypted        | the sudo secret is never silently lost                 | D11 / C3         |
| US11 | owner with an env-managed KEK                              | a clear refusal, plus guidance, for automatic KEK rotation                                       | the deployment never ends up on a key it doesn't have  | D9 / C5          |
| US12 | user with OAuth connections                                | refresh to keep working atomically on encrypted rows                                             | single-use refresh tokens are never lost               | C8               |
